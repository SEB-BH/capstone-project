## Overview

The Capstone is intended to simulate real software development work. Unlike earlier unit projects, there is **not one required technology stack or feature checklist for every project**.

Your solution should use technologies that make sense for the problem you are solving. Your technical scope must be appropriately challenging for a Capstone project and must be approved by the instructional team.

> ❗ General Assembly has a zero-plagiarism policy. Your project's code and project work must be substantially your own or your team's. You may use documentation, libraries, examples, and generic snippets appropriately, but you must understand and be able to explain the work you submit.

## Required Capstone deliverables

> ✅ **Any missing or incomplete deliverable requires a redo. All six deliverables must be complete to pass the Capstone.**

1. **Discovery Brief**
2. **Project Plan & Scope Approval**
3. **Midpoint Checkpoint & Retro**
4. **Testing & Feedback**
5. **Final Project & Handoff/Launch**
6. **Capstone Presentation**

See [Project Deliverables](../project-deliverables/README.md) for details and dates.

## Technical execution

> ✅ Your implementation must demonstrate an instructor-approved level of technical effort appropriate to the problem being solved.

- The project addresses the approved problem and target user/client need.
- The technical scope is appropriate for a Capstone project and is approved by the instructional team.
- Technology choices make sense for the solution rather than being added only to satisfy a checklist.
- The working product implements the approved MVP or a documented, re-approved revision of that MVP.
- Core functionality works reliably enough to demonstrate and deliver.
- The project does not expose secret keys, passwords, tokens, or other sensitive credentials.
- Code and project files are organized and readable using conventions appropriate to the chosen technologies.
- The project can be run or used without avoidable terminal, console, or application errors.
- The team can explain the major technical decisions and the flow of the application/product.

## Scope changes

Client requests, discoveries, technical blockers, and user feedback may change the project during the two weeks. This is normal.

After scope approval:

- New requirements should be documented before being accepted into the sprint.
- The team should consider the effect on the MVP, timeline, and existing backlog.
- Significant changes should be reviewed with the instructional team.
- A client request does **not** automatically become required work simply because it was requested.

## UI/UX and accessibility

For projects with a user-facing interface:

- The product has a clear and consistent visual design.
- A first-time user can understand how to navigate and use the core product.
- Layout and styling are responsive enough for the intended use case.
- Text and interactive elements have appropriate contrast.
- Images include appropriate alternative text when needed.
- Forms, buttons, links, and interactive elements are clear and usable.
- Important interface states such as errors, loading, success, or empty content are handled where appropriate.

## Testing and validation

- The team tests the MVP before final delivery.
- The project is reviewed or tested by someone outside the development team.
- Feedback and issues are documented.
- The team makes at least one evidence-based decision in response to feedback.
- The team documents feedback it intentionally does not implement and why, when applicable.

## Git and GitHub

> ✅ Git/GitHub is a core part of demonstrating professional project work.

- The repository or repositories are appropriately named and accessible to the instructional team.
- Git history dates back to the beginning of development work. If a repo is replaced, the earlier repo should be preserved.
- Commit messages describe meaningful work.
- Commits are made throughout the project rather than appearing only near the deadline.
- Team projects show meaningful contributions from the team members.
- Secret credentials and environment files are not committed.

## Documentation

Your primary README or equivalent project documentation should include:

- Project/startup/client name and a concise description.
- Screenshot, logo, or other visual representation where appropriate.
- Link to the deployed/published product where appropriate.
- Link to project planning materials.
- Setup/run instructions for technical projects.
- Technologies and major services used.
- Attributions for external assets or resources when required.
- Known issues or limitations.
- Future enhancements or recommended next steps.

Track-specific delivery requirements are listed in the [Client Track](../client-track/README.md) and [Startup Track](../startup-track/README.md) guides.

## Presentation

> ✅ Presentation requirements are required to pass.

- Present on Thursday, September 3, 2026.
- Prepare and use a slide deck.
- Present for approximately **8-10 minutes**, followed by **2-3 minutes of questions**.
- Include a live product demonstration when practical. Have a backup plan such as screenshots or a short recording in case the live demo fails.
- Explain the problem, discovery/research, proposed solution, development process, feedback/iteration, technical highlights, challenges, and next steps.
- Client Track opening and closing slides include the bootcamp logo and client logo.
- Startup Track opening and closing slides include the bootcamp logo and startup logo.
- Every team member participates in the presentation and discusses or demonstrates work they meaningfully contributed to.
